# Project context

Generated from a reviewed Context Pack.

## Current objective
Prepare the v1 public-launch positioning and the next steps to ship it, using only claims that are true today.

## Phase
Plan

## Project summary
A small team is launching a developer tool. Early users bounce off a feature-list homepage; the team needs one sharp promise and an honest launch that doesn't overclaim.

## Project rules
- Every public claim must be true today — no vaporware or unreleased capabilities.
- One promise in the hero, not a feature list.
- Do not overstate what the hosted platform does versus the open-source piece.

## Boundaries
- Draft launch copy + the plan only; do not publish the site or post anything.
- Use only real, confirmed product capabilities.

## Approved decisions
- **Lead with one promise, not a feature list** — The hero states a single outcome the product delivers today; features live below the fold.
  - Why: In user interviews, first-time visitors skimmed feature lists and left without understanding the core value.
  - Tradeoff: Some real capabilities won't be front-and-centre at launch; accepted for a clearer first impression.
  - Outcome: Approved as the launch direction.
  - Backed by: First-time visitors understood the product faster when shown one outcome instead of a feature list

## Relevant sources
- [Positioning: make your product easy to understand (April Dunford)](https://www.aprildunford.com/post/positioning) — _reputable_

## Files or areas to avoid
- A feature-dump homepage.
- Claiming roadmap items as if they already ship.

## Open questions
- Which of the two candidate taglines converts better in a quick test?
- Is pricing ready for launch, or should v1 be waitlist-only?

## Definition of done
A launch page whose hero is a single true promise backed by one concrete example, with no claim that isn't shippable today, and a clear go/no-go on waitlist vs. open signup.

## When uncertain
Ask for clarification rather than changing unrelated areas. Preserve the accepted direction.
